# UI 走查与优化方案 — 2026-09-26

基线：线上 `helm.easymeta.au`，`v0.30.23`。走查范围包括 Admin 全部 12 个页面、Portal 全部 7 个页面，以及首次安装向导。
两种屏幕都实测过：MacBook 屏幕视口 **1440×812**，外接 Dell 模拟视口 **2560×1440**。
截图存放在本地 `.playwright-mcp/audit/`（已被 gitignore，不入库）。

## 结论

1. **小屏上信息溢出，大屏上表单被拉得过宽**，两类问题同时存在，根源也相同：内容区没有宽度策略，每一列都平铺展示。
   - 在 1440 下，内容区只有 1118px 宽，而 Requests 表需要 1966px，Keys 表 1868px，Providers 表 1652px，Key 详情里的请求表 1544px。右侧的 Serving、Cost、Tokens、Actions 等列都要横向滚动才能看到。
   - 在 2560 下表格能放下，但 Settings 表单被拉到约 1500px 宽，Portal Account 页的标签和值隔了将近 1900px，难以对应着看。
2. **数据是齐的，只是缺少层次**。每一行都把所有字段平铺出来，比如 Keys 每行 3 行文字、6 个按钮，Requests 的路由列每行 3 行。结果主次不分，行高也被撑到 80–140px。
3. **配置页太长**。Lanes 有 27 条 lane，全部以展开的表单列出，页面高约 15,500px（约 20 屏）。Policies 每条规则约占 480px。
4. **Portal 用户想看的信息不全**：没有按天的用量明细，没有按模型的请求数和费用表；请求详情里缺时间、请求模型、推理强度、TTFT/TPS 和 fallback 过程。
5. **安装向导的 key 验证确实有 bug**，而且不止一个，详见 §4。
6. **大量配置只能改 YAML 或环境变量**，详见 §5。

## 1. 全局问题（Admin 与 Portal 通用）

| # | 问题 | 位置 | 方向 |

## 2. Admin 逐页

### Dashboard
- KPI 分两排：第一排 5 张卡，第二排 4 张卡，两排宽度不齐。改成一排 5 张主 KPI，Token 细分挪进 "Token usage" 图表的图例里。
- "Token usage over time" 的 Output 曲线贴着 0，基本看不见（输入量是输出量的 170 倍）。考虑 Output 和 Cached 单独用第二个 Y 轴，或者只画 Input/Cached 面积，Output 用柱状。
- 最近请求表：路由列每行 3 行，行高约 86px。精简为 时间 · 状态 · Key · 模型 · Lane · 费用，整行可点。
- 底部 "Manage" 的 5 张卡片和侧边栏导航重复，可以删掉。

### Requests（列表）
- 共 9 列，Session 列显示两段 hash，没什么信息量。默认列定为：时间、状态、Key、模型（在第二行用小字写 requested→served）、Lane、Tokens（↑↓ 加缓存）、耗时、费用。Session、Serving 账户、Request body、Request ID 放进展开区或详情页。
- "Decided by" 图例一直占着一整块，改为表头上的 `ⓘ` 提示。
- 筛选区的 Apply 和 Reset 单独占一行，应该和筛选项放在同一行。

### Request 详情
- 结构清楚，但太长：共 10 个区块，还有两个 JSON 查看器。建议顶部放一张 **摘要卡**，内容是 状态、模型（requested → served）、Lane、推理强度、耗时、TTFT、TPS、Tokens 和费用，下面用 Tabs 分成 **Routing / Usage & Cost / Request / Response**。
- "Lane candidate chain" 一次展开 14 个候选。默认只显示实际尝试过的几个，加一个 "+N more" 展开其余。
- "Request" 区块在没有抓取正文时，只显示 4 个字段的 JSON 树，外加一个大空框。这种情况下直接用一行说明代替。

### Lanes
- 页面约 20 屏高，全部 27 条 lane 都是展开的表单。改成 **列表加编辑抽屉**：每行显示 名称 · 用途 · 主模型 · fallback 数量 · 推理强度，点击后在右侧抽屉里用 LaneEditor 编辑。
- 每张卡片右上角那个灰色的 purpose 标签，应该作为副标题。

### Policies
- 每条规则的卡片都重复 "first match wins — lower number = higher priority" 这句说明，只在页面顶部说一次就够了。
- 规则卡片改成紧凑的一行 "当 [条件] → 强制 [lane] / 推理强度 [x]"，点击后展开编辑。
- 右下角浮动的保存条会盖住最后一张卡片，底部要留出安全区。

### Classifier
- 候选行的 "Move up / Move down / Remove" 是三个文字按钮，换成拖拽手柄或图标按钮。
- 有 7 类高级字段在 UI 里没有入口：momentum、task_keywords、tool_prefixes、overrides、language、sigmoid_k、extra_body。详见 §5。

### API Keys（列表）
- 共 10 列、6 个操作。精简列为：名称、Key 前缀、状态、今日用量（请求 · 费用 · 错误）、非默认的限制（G8）、操作（Details 加 `⋯`）。
- root key 那行 "Management plane only" 的警告换成 badge 加 tooltip。

### Key 详情
- 配置区和用量区都不错。底部的请求表跟 Requests 页溢出一样，复用同一个表格组件即可。

### Providers
- 表格 1652px 宽，而且 Actions 列竖着堆 3–4 个按钮。改成卡片列表：每张卡片包括 账户头（类型 · 邮箱 · 套餐）、状态、今日用量、配额进度条、模型 chips（折叠显示），以及 "Test" 主按钮加 `⋯` 菜单。
- "Account usage strategy" 放到页头右侧做一个紧凑的下拉框。

### Provider 详情
- 左上角单独一个 "Weekly" 按钮，下面又有一组 Period/Daily/Weekly 切换，两者看起来重复，令人困惑。
- 柱状图没有 X/Y 轴标签，也没有 hover 数值。

### Memory
- 状况良好。"All memory" 副标题用了等宽字体，改回正文字体即可。

### Settings
- 这是最长的表单。建议加锚点目录（Routing / Rate limiting / Queueing / Logging / Retention / Cleanup），页面铺满全屏。
- 两个字段都叫 "Queue wait timeout (ms)"，一个超时返回 429，另一个返回 503，语义不同却同名。要改成不同的名字。
- 数字字段只写 "0 means unlimited"，没有写单位的换算。输入框后面加单位后缀（ms/s/天）。

## 3. Portal（key 持有者自助门户）

用户最关心四件事：**每天用了多少、用了哪些模型、明细是什么、每次请求的详情**。现状如下：

| 需求 | 现状 | 缺口 | 方案 |
|---|---|---|---|
| 每天用量 | Overview 有 KPI 和当天按小时的 token 曲线 | 选 7d/30d 时没有**按天**的明细（请求数、tokens、费用） | 加 "Daily usage" 柱状图（费用和 tokens 可切换）以及按天明细表，范围 ≥7d 时默认按天 |
| 用的什么模型 | 只有一个 "Tokens by model" 甜甜圈图 | 看不到每个模型的请求数、费用、平均耗时 | 甜甜圈旁边加 "By model" 表：模型 · 请求 · tokens · 费用 · 占比 |
| 明细 | Requests 列表：时间、模型、lane、状态、耗时、tokens、费用 | tokens 只有总数；耗时显示成 `4642ms` | tokens 拆成 ↑输入 ↓输出 + 缓存；耗时用 s；加 TTFT |
| 每笔请求详情 | 模型、Lane、状态、耗时、token 表、费用表 | **缺时间**、requested vs served 模型、推理强度、TTFT/TPS、fallback 尝试过程；费用表里的 "Routing — / Eval —" 对用户没有意义 | 与 Admin 的摘要卡对齐（去掉内部字段：账户邮箱、候选链）；费用只保留合计，外加输入/输出/缓存三项的单价拆分 |
| Account | 只读的限制列表 | 大屏上标签和值距离过远 | 宽屏三张卡并排、卡内两列 description list；预算和限额用进度条表示 "已用 / 上限" |

另外两点：登录后顶栏没有语言切换；Account 页不在顶部导航里，只能从右上角 key 下拉进入。

## 4. 安装向导：DeepSeek key 验证失败 —— 确认是 bug

向导是 `apps/gateway/src/setup.ts` 里的内联 HTML，不属于 SvelteKit admin。验证流程如下：`POST /setup/api/test-provider` → `testStaticProviderKey`（`apps/gateway/src/server.ts`）→ 调用 `https://api.deepseek.com/v1/chat/completions`，模型取 `models[0]`，`max_tokens: 1`。

以下问题已从代码确认：
1. **有效的 key 因为余额为 0 被判成失败**。只要返回非 2xx 就算失败，而 DeepSeek 对新账户、无余额的 key 返回 **402 Insufficient Balance**。"Finish setup" 又要求 key 必须测试通过（`provider_test_required`），所以用户连保存都保存不了。OpenRouter 的 key 没有余额时同理，因为它的 `models[0]` 是付费模型。
2. **错误详情被丢掉了**。`UpstreamError` 的 message 只有 `upstream returned <status>`，上游的 body（比如 "Authentication Fails" 或 "Insufficient Balance"）虽然存在 `providerRaw` 里，但没有展示。用户分不清到底是 key 错了还是没钱。
3. **粘贴的 key 没有 trim**。多一个前导空格会变成 `Bearer  sk-…`；key 里夹着换行时，`fetch` 会直接抛错。
4. **测试模型取 `models[0]`，对其他 provider 也不对**：ZenMux 的第一个模型是图像模型 `openai/gpt-image-2`，Gemini 是 `gemini-3.1-flash-image`，OpenAI 是 `gpt-6-astra`（普通 key 未必有权限）。

此外还有几个疑似问题：15s 超时加上过载重试，高峰期可能超时；egress 的 undici Agent 不读 `HTTPS_PROXY`，走代理的用户会连不上。

修复方案（最小改动）：先 trim key；401/403 才判为无效 key，402/429 判为 "key 有效，但余额或速率受限"，给出警告并允许保存；422 响应里带上脱敏后的上游 `error.message`；测试模型改为按 provider 显式指定的低价 chat 模型，或者改用 `GET /models` 探测。

向导的视觉也需要统一：它有一套自己的 CSS，主按钮用的是 brand 靛蓝，而 admin 的主按钮是 `--color-action` slate；进度条的第 2 段是写死的静态高亮；也没有 i18n。

## 5. "所有配置都能在 UI 改" —— 现状与策略

**现在 UI 能改的**：Lanes、Policies（写回 YAML）、Classifier（部分字段）、System Settings（存 DB 的 `config_kv`）、API Keys、OAuth 订阅账户。
**只能改 YAML 或环境变量的**：`providers.yaml`（API-key 类上游）、`model-aliases.yaml`、`pricing.yaml`、`capabilities.yaml`、`memory.yaml`、`runtime.request_timeout_ms / sse_heartbeat_ms / signal_feedback / store`、`server`、`auth`，以及约 30 个 `HELM_*` 调优变量（memory worker、signals、write queue、auth cache 等）。

### 策略：三类配置分别处理，不强行塞进同一个地方

| 类别 | 例子 | 存储 | UI 行为 |
|---|---|---|---|
| **A. 路由规则类**（配置即代码） | lanes、policies、classifier、model-aliases、providers（不含密钥）、pricing/capabilities 覆盖项 | 维持 **YAML 写回**（现有 `rule-store` + `yaml-writeback`），git 可审计 | 完整编辑器；保存时做**跨文件引用校验**，比如删除被 alias 或 policy 引用的 lane 时直接拒绝，而不是拖到下次启动才 fail-closed |
| **B. 运行时调优类** | 超时、心跳、signal feedback、memory LLM/worker/forgetting、各种 `HELM_*` 调优项 | 归入 DB 的 **runtime settings**（`config_kv`），YAML 和 env 只作为初始值 | 在 Settings 里新增分组；页面标明 "当前生效值来源：DB / YAML / env" |
| **C. 引导与密钥类** | `server.*`、`auth.*`、`HELM_OAUTH_ENC_KEY`、admin 密码、store URL、TLS/undici | 保持 env-only | UI **只读展示**，并标出 "需重启 / 需改环境变量" |

Provider API key 属于特殊情况。安装向导已经会把 key 写进 `helm-managed-env.json`，UI 可以复用这条路径，改为加密存储，但界面上只显示 "已配置 / 未配置"，永不回显明文。

有两个已知风险要一并处理：
1. **DB 覆盖 YAML 让人困惑**：一旦在 Settings 保存过 rate limit，再改 YAML 或 env 就不生效了。在 UI 上显示来源，并提供 "重置为文件默认值" 按钮。
2. **YAML 写回的副作用**：数组里的注释会丢失，schema 默认值会被写进文件。这类行为要在 UI 上说明，或者只写回用户显式改动过的字段。

## 6. 设计原则（验收标准）

- **两种屏幕都要达标**：在 1440×812 下，主表格不出现横向滚动；在 2560×1440 下，页面铺满全屏，不设最大宽度。
- **首屏回答核心问题**：每页顶部是 1 行标题、1 行说明和主操作，数据紧跟其后；说明性文字放 tooltip 或折叠区。
- **只显示有意义的信息**：默认值、重复值、内部 ID 放到二级展示。
- **统一组件**：PageHeader、DataTable（列优先级、行内展开、整行点击）、ActionMenu（`⋯`）、StatCard、DescriptionList、FormSection（多列排布）、RangeFilter（合并为一套）。
- **不删功能**：所有现有操作、字段和 testid 都保留（`apps/gateway/e2e` 会硬断言 testid），只调整展示层级。
- **i18n**：7 个 locale 的 key 集合保持一致（CI 门禁）。

## 7. 实施分期

| 期 | 内容 | 规模 |
|---|---|---|
| **P0** | 修复安装向导 key 验证（§4 的 1–4 点），先写测试（TDD） | 小，可以单独发版 |
| **P1** | 布局原语：共享 token、PageHeader、全屏页面外壳、DataTable 列优先级 + 抽屉、ActionMenu、RangeFilter 合并 | 中，是后续各期的基础 |
| **P2** | Admin 数据页：Requests、请求详情、Dashboard、Keys、Key 详情、Providers、Provider 详情 | 大 |
| **P3** | Admin 配置页：Lanes（列表 + 抽屉）、Policies（紧凑行）、Classifier、Settings（锚点目录） | 中 |
| **P4** | Portal：按天用量、按模型表、请求列表与详情补全、Account 布局、语言切换 | 中 |
| **P5** | 安装向导视觉统一和 i18n | 小 |
| **P6** | 配置 UI 化：先做 B 类（进 runtime settings），再做 A 类（providers、aliases、pricing/capabilities 编辑器，加跨文件校验），C 类只读展示 | 大，分多个 PR |

每一期都按同样的方式验收：定向跑 Vitest；在两种视口下用 Playwright 截图对比；跑 `apps/gateway/e2e` 相关 spec。
